Apache Fineract replaces the legacy Flyway tool with Liquibase for all schema management. Migrations run automatically at application startup via `TenantDatabaseUpgradeService`, which upgrades both the **tenant store** (the registry database) and each **individual tenant** database. This page covers every migration file, the include hierarchy, multi-database contexts, and the naming conventions for adding new migrations.

---

## Top-Level Structure

```
fineract-provider/src/main/resources/db/changelog/
├── db.changelog-master.xml          ← master entry point (referenced by Spring)
├── tenant/
│   ├── changelog-tenant.xml         ← normal upgrade path, includes parts/0003..latest
│   ├── initial-switch-changelog-tenant.xml  ← one-time Flyway→Liquibase migration (0001+0002)
│   ├── final-changelog-tenant.xml   ← post-upgrade constraints (0146)
│   ├── parts/                       ← 236 numbered changesets
│   └── upgrades/                    ← legacy Flyway upgrade helpers (0000_upgrade_to_1.5.xml, 1.6.xml)
└── tenant-store/
    ├── changelog-tenant-store.xml   ← tenant store upgrade path, includes parts/0003..latest
    ├── initial-switch-changelog-tenant-store.xml
    ├── parts/                       ← 12 numbered changesets
    └── upgrades/
```

<Note>
`db.changelog-master.xml` is no longer used as the direct Liquibase entry point. Instead, `ExtendedSpringLiquibaseFactory` constructs `SpringLiquibase` beans pointing to the appropriate `changelog-*.xml` files based on context (`tenant_store_db`, `tenant_db`, `initial_switch`).
</Note>

## Runtime Execution

### TenantDatabaseUpgradeService

**File:** `fineract-provider/src/main/java/org/apache/fineract/infrastructure/core/service/migration/TenantDatabaseUpgradeService.java`

This `@Service` implements `InitializingBean`. Its `afterPropertiesSet()` fires on every server start:

```
afterPropertiesSet()
  ├─ upgradeTenantStore()
  │    ├─ if first Liquibase migration:
  │    │    liquibaseFactory.create(tenantDataSource, "tenant_store_db", "initial_switch")
  │    │    applyInitialLiquibase(...)   ← runs 0001+0002 with initial_switch context
  │    └─ liquibaseFactory.create(tenantDataSource, "tenant_store_db")
  │         SpringLiquibase.afterPropertiesSet()  ← runs 0003..latest
  └─ upgradeIndividualTenants()
       ├─ for each tenant in tenants table:
       │    tenantDataSourceFactory.create(tenant)
       │    if first Liquibase migration:
       │         liquibaseFactory.create(ds, "tenant_db", "initial_switch")
       │         applyInitialLiquibase(...)
       │    liquibaseFactory.create(ds, "tenant_db")
       │    SpringLiquibase.afterPropertiesSet()
       └─ parallel execution via ThreadPoolTaskExecutor
```

**Key constants defined in `TenantDatabaseUpgradeService`:**

| Constant | Value |
|----------|-------|
| `TENANT_STORE_DB_CONTEXT` | `tenant_store_db` |
| `INITIAL_SWITCH_CONTEXT` | `initial_switch` |
| `TENANT_DB_CONTEXT` | `tenant_db` |
| `CUSTOM_CHANGELOG_CONTEXT` | `custom_changelog` |

Liquibase is **skipped** when:
1. `databaseStateVerifier.isLiquibaseDisabled()` returns `true`
2. The instance is a read-only mode instance (`!fineractProperties.getMode().isWriteEnabled()`)

### ExtendedSpringLiquibaseFactory

**File:** `fineract-provider/src/main/java/org/apache/fineract/infrastructure/core/service/migration/ExtendedSpringLiquibaseFactory.java`

Constructs `ExtendedSpringLiquibase` instances, adding the database-type context (`mysql` or `postgresql`) from `DatabaseAwareMigrationContextProvider` plus any active Spring profiles.

### FineractLiquibaseOnlyApplicationConfiguration

**File:** `fineract-provider/src/main/java/org/apache/fineract/infrastructure/core/boot/FineractLiquibaseOnlyApplicationConfiguration.java`

An alternative Spring application configuration activated by the `liquibase-only` Spring profile (via `FineractLiquibaseOnlyApplicationCondition`). Only scans migration packages:
- `org.apache.fineract.infrastructure.core.service.migration`
- `org.apache.fineract.infrastructure.core.service.database`
- `org.apache.fineract.infrastructure.core.service.tenant`

This allows running Liquibase migrations in isolation (CI, pre-deployment) without starting the full application context.

## PostgreSQL vs MySQL Handling

`DatabaseAwareMigrationContextProvider` maps `DatabaseType.MYSQL → "mysql"` and `DatabaseType.POSTGRESQL → "postgresql"`.

Each migration changeset that differs between databases uses a `context` attribute:

```xml
<!-- MySQL-specific changeset -->
<changeSet author="fineract" id="1" context="mysql">
    <createTable tableName="m_delinquency_range"> ... </createTable>
</changeSet>

<!-- PostgreSQL-specific changeset -->
<changeSet author="fineract" id="1-postgresql" context="postgresql">
    <sql>CREATE TABLE ...</sql>
</changeSet>
```

The `initial_switch` context is used only for the Flyway→Liquibase migration changesets in `0001_initial_schema.xml` and `0002_initial_data.xml` to prevent re-running them on databases that have already been set up.

## How to Add a New Migration

<Steps>
  <Step title="Determine the next number">
    Find the highest numbered file in `fineract-provider/src/main/resources/db/changelog/tenant/parts/`
    and increment by one. As of writing, the latest is `0236`.
  </Step>
  <Step title="Create the file">
    Create `parts/NNNN_descriptive_name.xml` following the naming pattern. Use underscores, all
    lowercase. The name must describe the change, not the date.
  </Step>
  <Step title="Write the changeset XML">
    Use Liquibase 4.1 schema. Include separate changesets for MySQL and PostgreSQL if needed:

    ```xml
    <databaseChangeLog xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
                       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
                       xsi:schemaLocation="...">
        <changeSet author="fineract" id="1" context="mysql">
            <!-- MySQL-specific DDL -->
        </changeSet>
        <changeSet author="fineract" id="1-postgresql" context="postgresql">
            <!-- PostgreSQL-specific DDL -->
        </changeSet>
    </databaseChangeLog>
    ```

    For database-agnostic changes, omit the `context` attribute.
  </Step>
  <Step title="Include in changelog-tenant.xml">
    Add the include at the bottom of
    `fineract-provider/src/main/resources/db/changelog/tenant/changelog-tenant.xml`:

    ```xml
    <include file="parts/NNNN_your_change.xml" relativeToChangelogFile="true"/>
    ```
  </Step>
  <Step title="Test both databases">
    Run the integration tests with both MySQL and PostgreSQL profiles to verify your changeset
    applies cleanly. Check `TenantDatabaseUpgradeService` log output on startup.
  </Step>
</Steps>

<Warning>
Never modify an existing changeset after it has been merged. Liquibase checksums existing changesets — modifying them causes `ValidationFailedException` on startup. Always add a new changeset to fix a previous change.
</Warning>

## Initial vs Upgrade vs Final Changelogs

| Changelog File | Liquibase Context | When Used |
|---------------|-------------------|-----------|
| `initial-switch-changelog-tenant.xml` | `initial_switch` | First time a database is migrated from Flyway — runs `0001` and `0002` only |
| `changelog-tenant.xml` | `tenant_db` (+ `mysql`/`postgresql`) | Every normal startup — runs `0003` through latest |
| `final-changelog-tenant.xml` | `tenant_db` | After `changelog-tenant.xml` — applies deferred constraints from `0146` |

The `initial_switch` context is special: `TenantDatabaseStateVerifier.isFirstLiquibaseMigration()` detects whether the `DATABASECHANGELOG` table exists. If it does not, it runs the initial switch path first to create the baseline, then the normal path continues from `0003`.
