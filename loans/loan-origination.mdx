The `fineract-loan-origination` module provides a registry for **loan originators** — the third-party entities (brokers, aggregators, direct channels) that submitted a loan application to the financial institution. It is a purpose-built, conditionally-activated module that enriches loan-related Avro events with originator metadata, enabling downstream revenue-sharing, analytics, and regulatory reporting without polluting the core loan domain.

## Scope and Purpose

An **originator** in Fineract represents any external party responsible for sourcing a loan. The module manages:
- A registry of originator records (`m_loan_originator`) with type and channel classifications.
- A mapping table (`m_loan_originator_mapping`) that links an originator to a specific loan at submission time.
- Enrichment of Avro event payloads (`LoanAccountDataV1`, `LoanTransactionDataV1`, `LoanRepaymentDueDataV1`, etc.) with originator details for event-driven consumers.

The entire module is **conditionally active** — it only registers beans and exposes endpoints when `fineract.module.loan-origination.enabled=true` is set in application properties.

## Domain Entities

### `LoanOriginator`
```
fineract-loan-origination/.../domain/LoanOriginator.java
Table: m_loan_originator
```

```java
@Entity @Table(name = "m_loan_originator")
public class LoanOriginator extends AbstractAuditableWithUTCDateTimeCustom<Long> {

    @Column(name = "external_id", nullable = false, length = 100, unique = true)
    private ExternalId externalId;          // unique business identifier

    @Column(name = "name", length = 255)
    private String name;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private LoanOriginatorStatus status;    // ACTIVE | PENDING | INACTIVE

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "originator_type_cv_id")
    private CodeValue originatorType;       // from code "LoanOriginatorType"

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "channel_type_cv_id")
    private CodeValue channelType;          // from code "LoanOriginationChannelType"
}
```

Factory method: `LoanOriginator.create(ExternalId, String, LoanOriginatorStatus, CodeValue, CodeValue)`.

Mutation: `originator.update(name, status, originatorType, channelType)` — called by the write service on update.

### `LoanOriginatorMapping`
```
fineract-loan-origination/.../domain/LoanOriginatorMapping.java
Table: m_loan_originator_mapping
```

```java
@Entity @Table(name = "m_loan_originator_mapping")
public class LoanOriginatorMapping extends AbstractAuditableWithUTCDateTimeCustom<Long> {

    @Column(name = "loan_id", nullable = false)
    private Long loanId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "originator_id", nullable = false)
    private LoanOriginator originator;
}
```

A loan can have **multiple originator mappings** (e.g., broker + aggregator). The mapping uses `loanId` (not a FK `Loan` object) to avoid loading the full `Loan` aggregate.

### `LoanOriginatorStatus`
```
fineract-loan-origination/.../domain/LoanOriginatorStatus.java
```
`ACTIVE` — can be attached to loans.  
`PENDING` — created but not yet approved; cannot be attached.  
`INACTIVE` — deactivated; cannot be attached to new loans.

`LoanOriginatorStatus.fromString(String)` is case-insensitive.

| `DELETE /v1/loans/{loanId}/originators/{originatorId}` | Detach originator from loan |
| (+ 3 more DELETE variants with external IDs) | — |

**Attach/Detach constraints** (enforced in `LoanOriginatorWritePlatformServiceImpl`):
- The loan **must** be in `SUBMITTED_AND_PENDING_APPROVAL` status — throws `LoanNotInSubmittedStatusException` otherwise.
- The originator must be `ACTIVE` — throws `LoanOriginatorNotActiveException`.
- The mapping must not already exist — throws `LoanOriginatorMappingAlreadyExistsException`.

## Write Service: `LoanOriginatorWritePlatformServiceImpl`
```
fineract-loan-origination/.../service/LoanOriginatorWritePlatformServiceImpl.java
```

Key method signatures:

```java
// Registry CRUD
CommandProcessingResult create(JsonCommand command);
CommandProcessingResult update(Long id, JsonCommand command);
CommandProcessingResult delete(Long id);

// Loan-Originator mapping
CommandProcessingResult attachOriginatorToLoan(Long loanId, Long originatorId);
CommandProcessingResult detachOriginatorFromLoan(Long loanId, Long originatorId);
```

`attachOriginatorToLoan` internally:
1. Loads `Loan` via `LoanRepositoryWrapper.findOneWithNotFoundDetection(loanId)`.
2. Checks `loan.isSubmittedAndPendingApproval()` — rejects if not.
3. Loads `LoanOriginator` by ID — throws 404 if not found.
4. Checks `originator.getStatus() == LoanOriginatorStatus.ACTIVE` — rejects if not.
5. Checks `loanOriginatorMappingRepository.existsByLoanIdAndOriginatorId(loanId, originatorId)` — rejects duplicates.
6. Creates `LoanOriginatorMapping.create(loanId, originator)` and `saveAndFlush`.
7. Returns `CommandProcessingResult` with `resourceId=loanId`, `subResourceId=originatorId`.

## Origination Workflow

```mermaid
flowchart TD
    A[External system creates Loan Originator\nPOST /v1/loan-originators] --> B[LoanOriginator saved in m_loan_originator\nstatus=ACTIVE]
    B --> C[Client submits Loan Application\nPOST /v1/loans via LoanAccountApiResource]
    C --> D[Loan created in m_loan with\nstatus=SUBMITTED_AND_PENDING_APPROVAL]
    D --> E[Attach originator to loan\nPOST /v1/loans/{loanId}/originators/{originatorId}]
    E --> F{Loan in SUBMITTED status?\nOriginator ACTIVE?\nNo duplicate mapping?}
    F -- All pass --> G[LoanOriginatorMapping created\nm_loan_originator_mapping row]
    F -- Any fail --> H[Exception thrown:\nLoanNotInSubmittedStatusException\nor LoanOriginatorNotActiveException\nor LoanOriginatorMappingAlreadyExistsException]
    G --> I[Loan goes through approval lifecycle\nApprove → Disburse → Active]
    I --> J[Business events published]
    J --> K[DataEnricher pipeline runs]
    K --> L[LoanOriginatorDetailsResolver\nfetches mappings for loan ID]
    L --> M[OriginatorDetailsV1 appended to\nLoanAccountDataV1 Avro event]
    M --> N[Event published to Kafka/other consumers]
```

## Configuration

### Module Enable Property
```yaml
# application.properties or application.yml
fineract:
  module:
    loan-origination:
      enabled: true
```

`LoanOriginationModuleIsEnabledCondition` extends `PropertiesCondition` and reads `FineractProperties.getModule().getLoanOrigination().isEnabled()`. When `false`, **all** `@ConditionalOnProperty`-gated beans in the module are skipped: API resources, handlers, enrichers, services, and repositories are never registered.

### Code Value Setup

The module uses two code tables that must be configured in `m_code` / `m_code_value`:
- **`LoanOriginatorType`** (`LoanOriginatorApiConstants.ORIGINATOR_TYPE_CODE_NAME`) — e.g., "Broker", "Aggregator", "Direct"
- **`LoanOriginationChannelType`** (`LoanOriginatorApiConstants.CHANNEL_TYPE_CODE_NAME`) — e.g., "Online", "Branch", "API"

These are standard Fineract code values; pre-populate via the `/v1/codes/{codeId}/codevalues` endpoint.

## Gotchas & Invariants

<Warning>
  Attaching/detaching an originator is only allowed when the loan is in `SUBMITTED_AND_PENDING_APPROVAL` status. Once approved, the originator association is **immutable** through the API. To change originator after approval, a direct database operation or a custom service extension is required. This is by design for audit integrity.
</Warning>

<Note>
  `LoanOriginatorMapping` stores `loanId` as a plain `Long` column (not a `@ManyToOne` to `Loan`). This avoids loading the full `Loan` aggregate when resolving originator details for Avro enrichment. The repository query `findByLoanIdWithOriginatorDetails` uses a JOIN FETCH to eagerly load the `LoanOriginator` in a single query.
</Note>

<Warning>
  Deleting a `LoanOriginator` that has any `LoanOriginatorMapping` rows throws `LoanOriginatorCannotBeDeletedException`. The check is `loanOriginatorMappingRepository.existsByOriginatorId(id)`. To clean up: first detach from all loans (while they are in SUBMITTED status), then delete.
</Warning>

<Tip>
  The `LoanOriginatorData` class (the read DTO) is distinct from `LoanApplicationOriginatorData`. The former is the full registry view (used by `GET /v1/loan-originators`); the latter is a lighter projection used in loan application contexts. Do not confuse the two when adding new read endpoints.
</Tip>

<Note>
  All enrichers use `data.getId()` or `data.getLoanId()` (depending on the Avro schema) as the key to fetch originator mappings. The `LoanRepaymentDueDataV1OriginatorEnricher` casts `data.getLoanId()` to `Long` explicitly — ensure the Avro schema version in use stores `loanId` as a `Long`, not a `String`, or this cast will throw at runtime.
</Note>
